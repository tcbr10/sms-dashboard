# Micropay SMS dashboard

Hebrew RTL dashboard of SMS traffic, with manual sending by users an admin has authorized. Two Cloudflare Workers share one D1 database. Nothing is sent automatically, and no delivery-report processing is included. Existing delivery-report integrations must remain unchanged.

## Documentation basis and status

Adapted against the supplied offline Micropay documentation: incoming-SMS webhook (updated June 10, 2026), API conventions, send-SMS API and automation-trigger API. Source references: [incoming SMS](https://site.micropay.co.il/api/webhook-incoming-sms.php), [conventions](https://site.micropay.co.il/api/conventions.php), [send SMS](https://site.micropay.co.il/api/send-sms.php), [automation trigger](https://site.micropay.co.il/api/auto-webhook.php).

The documented incoming callback belongs to a Dynamic Text SMS service. It is not proof of the payload or acknowledgement used by an automation's outgoing HTTP action. The automation-trigger endpoint autoWebhook.php is the opposite direction: external systems invoke Micropay workflows. Do not call it to retrieve incoming SMS. Keep the planned incoming-automation forwarding approach; use the new adapter only if its forwarded fields match the documented callback, otherwise map to the normalized contract. Do not replace existing Dynamic Text services without verifying coexistence.

Code is not deployed or live-tested. Tests are included but must be run before production. No real account credentials, database IDs, numbers, or assignments are committed. Verify a real request, retries, timeouts, escaping and coexistence before enabling forwarding. The supplied webhook docs describe non-200 errors and technical email alerts, but do not establish a retry guarantee.

## Setup

Use Node 22 or later.

```sh
npm install
npm run typecheck
npm test
npx wrangler login
npx wrangler d1 create sms-dashboard
cp workers/dashboard/wrangler.jsonc.example workers/dashboard/wrangler.jsonc
cp workers/ingest/wrangler.jsonc.example workers/ingest/wrangler.jsonc
cp workers/links/wrangler.jsonc.example workers/links/wrangler.jsonc
```

The copied wrangler.jsonc files are git-ignored because they hold account-specific values; only the .example files are committed. Replace REPLACE_WITH_D1_DATABASE_ID in all three with the same database ID, then run npm run db:migrate. The other REPLACE_WITH values (Access settings and custom-domain hostnames) are covered below. Create the first admin and the first system number through D1 SQL; everything after that is managed on the dashboard's admin page. Emails are lowercase and trimmed; numbers are international.

```sql
INSERT INTO users(email,name,role,created_at) VALUES ('owner@example.com','Owner','admin',0) ON CONFLICT(email) DO UPDATE SET role='admin',active=1;
INSERT INTO system_numbers(number,label) VALUES ('+972501234567','Office');
```

## Ingestion secrets

The ingestion Worker is public and Micropay does not sign its callbacks, so every request must carry one of two secrets. These are our own secrets, NOT the Micropay account token. Generate each with `openssl rand -hex 32` (at least 32 characters are required) and store them as Worker secrets:

```sh
npx wrangler secret put INCOMING_TOKEN --config workers/ingest/wrangler.jsonc
npx wrangler secret put OUTGOING_TOKEN --config workers/ingest/wrangler.jsonc
```

- INCOMING_TOKEN authorizes incoming messages. Micropay can only be configured with a URL, so set the service's callback address to `https://YOUR-INGEST-HOST/hooks/micropay/incoming?token=INCOMING_TOKEN`.
- OUTGOING_TOKEN authorizes outgoing logs from your sending workflow.
- The normalized routes accept only an `Authorization: Bearer TOKEN` header; only the Micropay route also accepts `?token=`.

Treat the Micropay callback URL as a secret, since anything that records full URLs records the token. To rotate INCOMING_TOKEN, update the secret and the Micropay URL together; callbacks arriving in between fail, and Micropay may send its configured error SMS for them.

## Documented incoming callback

Dedicated route: GET or POST /hooks/micropay/incoming. POST accepts application/json or application/x-www-form-urlencoded. GET and forms must URL-encode free text; JSON must not URL-encode it. Bodies and GET query data are limited to 32 KiB. Duplicate form/query parameters, invalid encoding and mixed normalized/provider fields are rejected. Micropay automations build the JSON from a template and paste the message in unescaped, so multi-line messages (and messages with quotes) arrive as invalid JSON; this route escapes raw control characters inside strings and, if quotes still break the object, reads the known Micropay fields by name. Other routes keep strict JSON.

Field mapping:

| Micropay | Stored meaning |
| --- | --- |
| origsms | Full message body, including its keyword |
| phone | Customer/peer number |
| dest | Receiving system number |
| msgid | Stable incoming event ID, preserving leading zeros |

The adapter requires nonempty origsms and msgid; it never reconstructs full text from sms or code. cid, code, sms and net are not persisted. Local Israeli and digits-only international phone formats normalize to +country-number. dest is required and must be an active registered system number. The documented callback has no timestamp, so occurrence time uses receipt time with time_source=receipt.

After successful persistence, GET/form callbacks return exactly HTTP 200 with OK. JSON callbacks return HTTP 200 with {"reply":""}. These responses request NO automatic reply SMS. When an active bot flow answers the message, the reply text goes in instead ({"reply":"…"} or the plain text), and Micropay sends it to the customer; see the auto-reply bot below. Do not return the normalized ingestion response to a Dynamic Text service: arbitrary response text can become an SMS reply. Storage/authentication/validation errors return non-200 and never a false success; the documented Dynamic Text service may send its configured fixed error to the customer on non-200 responses.

Example:

```sh
curl -X POST "https://YOUR-INGEST-HOST/hooks/micropay/incoming?token=$INCOMING_TOKEN" \
 -H 'Content-Type: application/json' \
 --data '{"origsms":"שלום, אפשר פרטים?","phone":"0509876543","dest":"0501234567","msgid":"00705d38b642d5423","cid":"12762"}'
```

## Normalized events and outgoing logs

POST /hooks/incoming (INCOMING_TOKEN) and POST /events/outgoing (OUTGOING_TOKEN) accept normalized JSON with header authentication. system_number is required:

```json
{"event_id":"stable-workflow-id","system_number":"+972501234567","peer_number":"+972509876543","body":"שלום","occurred_at":"2026-10-06T09:40:00Z"}
```

Outgoing logs additionally require submission_status: pending, accepted, rejected, or unknown. Reuse the same event ID for updates. Final accepted/rejected states cannot regress. Retry logging failures WITHOUT resending SMS. Incoming normalized events without stable IDs remain separate; upstream retries can duplicate them. No raw payloads are stored and routine errors do not expose SMS bodies or tokens.

shared/micropay-submission.ts interprets an existing scheduleSms response without issuing any API call. It checks message=OK AND numeric status=1 for JSON, recognizes documented plain OK/validate variants, and treats ambiguous responses as unknown. ERROR denotes rejection. task_id is a campaign ID, NOT an individual message ID: retain it in the sending workflow's metadata, not provider_message_id. Status=1 alone is insufficient, and queue acceptance is not delivery. Log every concrete recipient/body separately for batches or listjson; a campaign acknowledgement does not enumerate recipients, pool membership, or personalized bodies.

When an incoming message is exactly one of the opt-out words in the settings (default הסר, הסרה, STOP, UNSUBSCRIBE; case, spaces and surrounding punctuation are ignored), the sender is added to the opt-out list. A failure of this step is logged and never fails the ingestion.

Deploy the configured ingestion Worker with npm run deploy:ingest. Do not change delivery-report URLs, add DLR ingestion, or automatically send SMS.

## Dashboard and operations

Set ACCESS_ISSUER to https://YOUR-TEAM.cloudflareaccess.com and ACCESS_AUD to your Access application's audience. Set the dashboard hostname in routes, protect it with an Access application and an explicit user policy, then deploy using npm run deploy:dashboard. Dashboard workers.dev and preview URLs stay disabled. Every request verifies the JWT issuer, audience, signature and expiry; email headers and query parameters are not identities. The verified email must then belong to an active row in users, otherwise the dashboard shows a no-access page. Because the users table is the allowlist, the Access policy may admit any email that completes its login (for example One-time PIN for everyone); adding or removing a user on the admin page then takes effect immediately. Every message query enforces D1 assignments; admins see every active number.

The UI is a table of messages, 100 per page with more loaded on scroll. Each user chooses the visible columns (time, direction, customer, each contact field, system number, message, status, sender, receive time); the choice is saved per user and is the default for exports. Clicking a column header opens a menu to sort by that column and filter it: a time range (last hour, last 24 hours, a typed number of recent hours up to 720, today, 7 or 30 days, or custom dates with optional hours and minutes), several values (direction, status, system number), or "contains" text (customer, message, sender, contact fields). Active filters appear as chips with a per-filter clear and a clear-all; on phones a Filter and sort dialog offers the same controls. Sorting and filtering are server-side with keyset cursors (base64url of UTF-8 JSON, so contact values in Hebrew page correctly), and the filter state is kept in the page URL. The search box also matches contact data. Summary counts come from /api/stats for the same filter. Visible tabs poll every 5 seconds by default, background tabs every 30 seconds, without overlapping requests; updated-time/ID cursors pick up new messages and status changes. Each open tab therefore makes about 12 small D1 queries a minute. textContent rendering, nonce CSP and no-store responses are retained. Display timezone and date-filter day and time boundaries are Asia/Jerusalem. In a custom range, a time without a date means today, the end time includes its whole minute, and an end date without a time includes the whole day.

Export (any user) writes every message matching the current filters and sort to Excel (.xlsx) or CSV, with the chosen columns. The browser fetches up to 50,000 rows in pages of 500 (export=1) and builds the file itself; the first page records an export entry with the filters and columns in audit_log. CSV is UTF-8 with a byte-order mark, and cells that look like formulas are prefixed with '. The export window also offers one row per number: the server groups the filtered messages by customer (group=peer, up to 50,000 customers) and returns each customer's contact data, message counts (total, incoming, outgoing), latest message (time, direction, text, system number) and opt-out state. A button ticks every contact field, including fields hidden from the table.

## Users, roles and the admin page

Admins (role admin) open /admin to manage users, system numbers, contacts, the opt-out list, settings and the activity log. Each user has a name, an active flag, an optional test number and, per system number, view or view-and-send access. Two more permissions apply to non-admins: sending to more than one recipient or from a file (can_bulk_send), and a limit on recipients per rolling 24 hours (daily_limit, or the default from settings). Admins see and may send from every active number without a daily limit. The system refuses to delete or demote the last active admin, and admins cannot remove their own rights. The users table marks users seen in the last two minutes as connected. Each number assignment can be restricted ("הגבלות" in the user dialog): only messages from a date and time onward, and only messages matching every condition, where a condition is a contact field equal to or containing a value, a bot answer (its saved meaning, or the answer itself) equal to or containing a value, message text containing a phrase, or a direction. Contact-field and bot-answer conditions apply to all of that customer's messages. The restriction is enforced on the server (scope.ts) for the table, counts, live updates, search, export, conversations, bot state and contact edits; sending is not restricted. Restricted users see a note in the table footer. Disconnect sets sessions_revoked_at: Access logins issued (JWT iat) before that moment are refused with a page asking the user to sign in again, and the admin can also disable the user in the same step. Every user can also sign out from the profile menu (the initials button in the header): POST /api/me/logout records user.logout in audit_log, then the browser goes to /cdn-cgi/access/logout, which ends the Access session on that device only. Every change, send and export is written to audit_log.

Contacts hold data per customer number in admin-defined fields (settings contact_fields, up to 20; Name and ID number by default). Admins manage the fields in Settings, or with "ניהול שדות" on the contacts tab, which the columns menu on the messages page links to (/admin#fields). Admins add, edit, delete and import them from CSV or Excel; the import matches file columns to fields by header name, repairs lost leading zeros, and either merges the file's non-empty values into existing contacts or skips existing ones. Users see contact data on the messages they can already see. Users with the can_edit_contacts permission (on by default, set per user on the admin page) and admins can also edit a customer's fields from a message's details (POST /api/contacts/save). Users may only edit customers that appear in messages on their active assigned numbers. The browser sends only the fields that changed, which are merged into the shared contact, so two people editing different fields don't overwrite each other; an empty value removes the field, and a contact left with no fields is deleted. Contact data such as ID numbers is personal information; exports that include it are recorded.

Settings: organization name, contact fields, default row spacing, live refresh interval (3 to 60 seconds), maximum recipients per send (up to 5,000), default daily limit, opt-out words, opt-out text appended to sends with more than one recipient, and whether non-Israeli recipients are allowed (off by default).

Message import (admins, tab "ייבוא הודעות") adds message history from an Excel or CSV file, for example messages that never arrived through the webhook. The browser guesses the columns from Hebrew or English headers (customer phone and message text are required; system number, date, separate time, direction, submission status and Micropay msgid are optional with defaults), reads dates day-first in Israel time (Excel date cells included), and previews the rows with each invalid row's reason. It uploads up to 12,000 rows per file in batches of 500 to /api/admin/imports/rows, after /api/admin/imports/start creates the import record. The server validates every row again (active registered system number, phone numbers, text up to 10,000 characters) and skips duplicates: a row with a msgid gets the same event key as the live webhook, and a row without one is skipped when the same number, customer, direction and text exists within 10 minutes of its time; its content-based key also makes uploading the same file again add nothing. Imported incoming replies that are exactly an opt-out word are added to the opt-out list. Imported messages carry import_id and show an "imported" tag. Undo (/api/admin/imports/undo) deletes exactly the messages one import added and leaves opt-outs in place. Nothing is ever sent. Each stored message costs about 8 rows written (the row and its indexes); the free plan allows 100,000 a day.

Phone numbers typed or imported anywhere (lists, recipients, contacts, message import, test numbers) go through one parser, parseRecipient() on the server and its twin parsePhone() in the browser, which tests keep identical. It removes invisible direction marks and punctuation, finds the number inside surrounding text, accepts 972 with or without a plus (also with the 0 kept after it), 00 prefixes and lost leading zeros, and checks Israeli lengths (05x and 07x have 10 digits, landlines 9). Cells with several numbers ("050… / 052…") are split. Every import reports each value it left out with the file row and reason (missing digits, Excel scientific notation, not a number, duplicate, already in the list), and the report downloads as CSV. List import can read one column or all columns.

Cloudflare Access sync: when CF_API_TOKEN (secret, permission Access: Apps and Policies - Edit), ACCESS_ACCOUNT_ID and ACCESS_POLICY_ID are set, adding, deleting, disabling or re-enabling a user rewrites the email rules of that Access policy to the list of active users. Other rule types in the policy are kept. A reusable policy is used directly; a policy inside an application is found through the application with the dashboard's ACCESS_AUD. A failed sync never blocks the user change: the admin sees the reason, the users tab shows the last result and a manual sync button, and every sync is in the activity log.

Webhook forwarding (admins, tab "העברה ל-Webhook"): a rule sends every incoming message of one system number, optionally only from listed senders, to an HTTPS address. Each rule picks a body format: JSON (event, id, msgid, system_number, system_label, from, body, occurred_at, received_at, contact) or Micropay's own webhook fields as a form post (origsms, phone, dest, msgid). Requests carry X-SMS-Delivery and X-SMS-Signature (sha256= HMAC of the body with the rule's secret), plus optional custom headers. The ingest Worker queues a delivery per matching rule after the message is stored and tries it after responding; a 2xx answer counts as delivered. Failures are retried by the ingest Worker's cron trigger (every minute) after 1, 5, 15, 60, 120, 240, 360, 360 and 480 minutes, ten attempts in all, then marked failed. Forwarding never changes what Micropay receives. Only live incoming messages are forwarded, not imports or outgoing messages. The tab shows the last 100 deliveries with resend, and a test button posts a sample.

Auto-reply bot (admins, tab "בוט"): a flow belongs to one system number and is a list of steps: a question with answer options (each option has the replies that match it, comma-separated, a meaning that is stored, and the next step), an open question (the answer is stored as typed), or a closing message. Answers can also be written to a contact field. A conversation (system number + customer) remembers its current step, so the same reply is read against the question asked last. A flow starts on any incoming message (one active flow per number), on a keyword (the whole message or its first word), or only from the compose window, where choosing a flow sends its first step and starts the conversation for the recipients. Replies are returned as the answer to Micropay's incoming-SMS webhook (JSON reply or plain text), so they need no API call, and each is logged as an outgoing message sent by "בוט". An unrecognized reply repeats the question twice, then the conversation ends; a conversation also ends after the flow's idle time (default 24 hours). Opt-out replies and opted-out customers end the conversation, and the bot never answers them. Users can turn the bot off or on for a customer from a message's details, or tick "turn the bot off" when sending; starting a flow from the compose window turns it back on for those recipients. A repeated webhook call for the same msgid returns the same reply without moving the conversation. Bot replies only work for messages that arrive through the Micropay webhook route. Micropay sends the webhook's answer as an SMS only for a Dynamic Text service; an automation's HTTP step ignores it. So each system number has a setting (numbers tab, bot_reply): "response" (default, Dynamic Text) returns the reply as the answer, and "api" (automation) answers the webhook with no reply and sends the reply through Micropay's scheduleSms API right after, recording the result on the logged reply. API replies need the MICROPAY_TOKEN secret on the ingest Worker too; without it they are logged as rejected. A repeated webhook call never sends an API reply again.

Answer replies (any flow): an answer option may have its own reply (say, up to 1,000 characters). When it is chosen, that reply is sent instead of the next step's text, and the conversation then ends or waits at the chosen next step, whose own text is used only to ask again after an unrecognized answer. Without a reply the next step's text is sent, as before.

A flow can also start with a first question sent by another system ("שאלה ראשונה ממערכת אחרת", trigger external): the bot does not send it, and a message from a customer who is in no conversation on that number is read as the answer to the flow's first step (which must be a question). Step 1 then holds the replies to the customer's first message: its question text is optional (sent only with the fallback after an unrecognized answer), and each answer can carry the bot's reply. A recognized answer is saved and the flow goes on; an unrecognized one gets the fallback text (and the question, if written), then the usual two repeats. A keyword flow still goes first, opted-out and blocked customers are ignored, and only one active flow per number may start on any message or this way. repeat_mode decides what happens when a customer who already went through the flow writes again: once (the default; flow_customers records who it read, and earlier answers to the flow count too) leaves them alone, always reads the message as an answer again. The reply is tagged in the chats page; first messages imported later appear before it as messages from another system.

Flow audience ("למי התהליך מיועד", migration 0016): a flow of any trigger except a dashboard send can be limited to a distribution list (a shared list or the admin's own). The bot starts it, or reads a first answer for it, only for customers on the list; others fall through to a flow for everyone on the number, and a flow with an audience wins over one without. Two active flows that answer every message (or share a keyword) clash only when they have the same audience. A conversation already under way continues. A list used as an audience cannot be deleted. In the flow dialog, "הוספת מספרים" adds numbers typed, pasted or read from a CSV/TXT/Excel file to the audience list (or makes a new shared list for the flow).

Recording a first message another system sent ("רישום הודעה" on the bot tab, `POST /api/admin/flows/record`, admins): pick the flow, the message as it was sent, when it was sent, and the numbers (a list, pasted numbers, or a file). Nothing is sent. Each number gets an outgoing message (sent by "מערכת אחרת", with the flow's first step noted on it) that opens its chat, is put at the flow's first step so replies continue the flow, and appears on the bot chats page. The browser sends 500 numbers per call under one record id, so repeating a call adds nothing; opted-out and bot-blocked numbers are skipped.

Bot chats (/chats, "שיחות בוט" in the header): every customer the bot has talked to on a number appears as a chat, newest activity first, with its state (in a conversation, ended, bot turned off, opted out), flow and latest message; it can be filtered by state and flow and searched by number or contact details. Opening one shows the messages as a chat (from /api/messages, so the user's numbers and view restrictions apply) with what the bot made of each reply: recognized (and as what), saved as a text answer, not recognized with the repeat count, or not recognized after which the bot stopped; bot questions show their answer options with the chosen one marked. The side panel shows the contact, the bot state (the step it waits on and when the conversation expires, or who turned the bot off) and the answers collected. A manual reply goes through /api/send and by default turns the bot off for that customer; the bot can be turned off or on from the header. Threads live in bot_threads (one row per customer and number), opened when a flow starts and touched by every later message, a bot block and a dashboard send, so the list and its live updates read by update time only; the state is worked out when read, so an expired conversation needs no write. What the bot did is kept in messages.bot: on a customer's message {flow,step,match,retry|gave_up} or {start}, on the bot's message {flow,step} with start, retry or end. A chat is listed only when the user can see at least one of its messages. Messages from before this change have no bot note, so they show without tags, but their answers still show in the side panel.

## Sending messages

Set the Micropay API token (created under account and sub-admin management, API tokens, with SMS permissions) as a dashboard secret. Without it, sending answers 503.

```sh
npx wrangler secret put MICROPAY_TOKEN --config workers/dashboard/wrangler.jsonc
```

POST /api/send takes {id, system_number, recipients, body}. The client generates the UUID id when the compose panel opens; the server claims it in the sends table before calling Micropay, so a retried or repeated request returns the earlier result and never sends twice. The server re-checks everything: send access to the number, bulk permission, maximum recipients, the 24-hour limit, valid and (unless allowed) Israeli numbers, duplicates, and the opt-out list. It then calls scheduleSms.php once with the system number as sender and the recipients in local format, interprets the answer with shared/micropay-submission.ts, and writes one outgoing message per recipient with sent_by and send_id. A timeout or unclear answer is recorded as unknown and never retried automatically. Accepted means Micropay queued the campaign, not that it was delivered. Writes to the dashboard (POST) must come from its own origin with a JSON body.

The compose panel accepts numbers separated by commas or new lines, a CSV, TXT or Excel .xlsx file (first worksheet; the column with the most phone numbers is chosen and can be changed), and distribution lists. Numbers that lost their leading zero in Excel are repaired. It shows recipients, invalid entries, characters and billed SMS (70 Hebrew characters for one SMS, 67 per part after that), and asks for a second confirmation before sending. A test send (test: true) goes to exactly one number, usually the user's saved test number, with the opt-out text a multi-recipient send would carry (bulk_preview); it counts toward the daily limit and is marked as a test.

Message variables: {field name} is replaced by the recipient's contact field with that name, {field name|default} uses the default when the field is empty, and {טלפון} inserts the recipient's number. The compose window has an "insert variable" menu and a preview for the first recipient (/api/send/preview). Micropay's API sends one text per call, so the server renders each recipient's text and groups recipients whose text comes out the same, one call per group, up to six at a time. Personalized sends are limited to 40 recipients per request because of the free plan's 50 outgoing calls per request, so the browser sends larger personalized sends in batches of 40, each with its own send ID; retrying after a failure resends only the batches that did not go out. bulk:true marks a batch of a larger send so the opt-out text is added. Each recipient's message row records its own text and result, and unknown variables are refused. Bot step texts support the same variables, rendered after the step's answer is saved.

Scheduled sends: the compose window's "שליחה מתוזמנת" takes a date and time (Israel time). POST /api/send with send_at checks permissions, recipients, variables and the flow, and stores the send in scheduled_sends. The ingest Worker's every-minute cron sends it through the same code as the send button (shared/dispatch.ts), checking the sender's permissions again and reading opt-outs, the daily limit and contact data at send time; it runs one batch per minute (the whole send, or 30 recipients of a personalized send without listjson) and takes turns with forwarding retries because of the free plan's per-invocation limits. Users see, move and cancel their own waiting sends ("מתוזמנות"; admins see everyone's) until the first batch goes out. Results (sent, unknown, rejected, skipped as opted out, or the error) appear in that list.

Single-call personalized sends: with the admin setting micropay_listjson on, a personalized send goes to Micropay as one call with listjson (each number with its own text) instead of a call per distinct text, so the browser no longer batches it. The setting is off by default; send a personalized test to your own phone before turning it on.

Tracked links: with the admin setting link_base ("כתובת הקישורים המקוצרים") set to the links Worker's address, the compose window shows "קיצור ומעקב קישורים" when the message contains a link (http://, https:// or www., with a dot in the host). With it checked (track_links:true), every link in each recipient's text is replaced by a short link of its own, link_base/<7-character code>. Links are found after variables are filled, so a link may contain variables; the opt-out text is never tracked. The links are stored in the links table in the same transaction that claims the send ID, before Micropay is called, and a code collision is retried with new codes. Because every recipient's text differs, a tracked send is batched like a personalized one (40 per request, 30 per cron run, or one listjson call). Scheduled sends keep track_links and create the links when they go out.

The links Worker (workers/links, its own short custom domain, no Access) answers GET /<code> with a 302 to the original address and counts the click after responding (waitUntil); unknown codes get a 404 page, HEAD requests are never counted, and responses are no-store, no-referrer and noindex. A click counts as probably automatic (a link preview, a carrier's or security scanner) when the user agent is empty or looks like a bot or preview fetcher, when it comes from a cloud provider's network (cf.asOrganization), or within 10 seconds of the link being created; content delivery networks are not treated as automatic because Apple's Private Relay sends real taps through them. People's taps increment messages.clicks and set clicked_at; automatic opens increment messages.auto_clicks (at most 5 per link). A repeat tap on the same link within 30 seconds is not counted again. Each counted click updates the message's updated_at, so open dashboards show it on their next poll. Only times and counts are stored, never IP addresses or user agents. The "לחיצות" column shows clicked / opened automatically only / not opened, can be filtered (clicks=clicked,auto,none), sorted and exported; messages without tracked links show "—". A counted click writes about three D1 rows, so the free plan's 100K rows written a day, shared with receiving messages, allows roughly 25K clicks a day.

Links tab (admin tab "קישורים", admins only, /api/admin/links*): general short links on the same address as the SMS links (link_base/<name>), for use anywhere, not only in messages. A link has a destination (http or https, up to 2,000 characters), an internal title and a name: chosen (2 to 40 lowercase English letters, digits or -, not starting or ending with -; x, api, admin, robots, favicon and www are reserved) or random (7 lowercase letters and digits). Names are unique across general and SMS links and can't be changed; the destination, title and on/off can. A link that is off shows "הקישור אינו פעיל" (410) and counts nothing; a deleted one shows not found and frees its name. Every click counts (there is no recipient to tell repeats apart), people apart from automatic opens, also per Israel-time day (short_link_days) for the 30-day bars. The same tab lists the links in sent messages, one row per send and address (link_groups: recipients, how many of them clicked, clicks), newest first, and an admin can change where a sent link leads: every recipient's personal link of that send follows at once, the message text stays as sent, and the click counts per recipient go on. The redirect reads the address from the group, so a change is one row. A send that goes out in batches (browser batches with batch_of, scheduled sends) is one group per address. The links Worker looks a path up among SMS link codes first, then among general links (lowercased).

Sender IDs (admin tab "זיהוי שולח"): what recipients see as the sender instead of the system number. Only admins add, verify, edit and remove them (/api/admin/senders*), and they choose which users may send as each one, from the sender's dialog or the user's ("זיהוי שולח מורשה"); admins may use them all. A phone number (Israeli landline or mobile) is verified through Micropay's senderVerify.php: Micropay sends a code to the number by SMS, voice call or automatically (POST with token, phone, type), and the code typed back (token, phone, code, desc) adds it to the Micropay account; a number Micropay already knows (PHONE_EXIST) is added without a code, and Micropay allows 2 SMS and 2 voice codes per number per 15 minutes. A text name (2 to 11 English letters, digits, space, + or *) has no approval API: it must be approved in Micropay's site, is registered as unconfirmed, and the first send with it marks it confirmed, or rejected when Micropay answers "sender id not approved". The compose window offers the user's sender IDs; the send goes to Micropay with from set to the sender ID (scheduleSms and listjson), is filed under the system number as usual, and records the sender on the send and its messages ("נשלחה בשם"). The permission is checked on every send and again when a scheduled send goes out. Replies to a sender ID don't reach this system, so a send with one can't start a bot flow, and a send to several recipients (or a test of one) needs the opt-out link text setting (optout_link_text, which must contain {קישור}) and link_base: instead of optout_text it ends with that text, where {קישור} is the recipient's own opt-out link link_base/x/<code>. Each customer has one code (optout_codes), reused by later sends. Opening the link on the links Worker only asks; the button (a POST) adds the number to the opt-out list with source "link", so link previews and scanners can't opt anyone out. The page shows only the last four digits of the number.

Distribution lists (/api/lists) belong to one user and are private, except lists an admin marks as shared, which every user can see and use but only admins can edit. A list holds up to 10,000 numbers; the compose panel expands selected lists into recipients, and the server validates every number as usual.

## Production checklist and backups

Before production, run CI, resolve dependencies and commit a package-lock.json, verify Access failures on every hostname, instrument all outgoing workflows, define retention, monitor ingestion failures and D1/Workers quotas, and schedule protected exports with restoration tests. Manual/uninstrumented outgoing messages and historical imports remain absent.

```sh
npx wrangler d1 export sms-dashboard --remote --output=backups/sms.sql --config workers/ingest/wrangler.jsonc
```

Create the backups directory first. Exports contain SMS content. Deleting retained messages also deletes deduplication keys, so late replays can reinsert expired messages. No scheduled retention or backup automation is configured by this repository.
